# Bloom Uninstall (Windows)

Fuente: `installer/uninstall/`. Destino acordado para el binario Windows: `installer/native/bin/win64/uninstall/bloom-uninstall.exe`; destino productivo previsto: `%LOCALAPPDATA%\BloomNucleus\bin\uninstall\bloom-uninstall.exe`. La integración con Build, Metamorph y el empaquetado de Setup corresponde a esos proyectos y queda pendiente de sus works respectivos.

## Versión

`VERSION` contiene la versión de producto (`1.0.0`) y se incorpora al binario Go. `scripts/build_number.txt` es el contador base y `scripts/build_number.{windows,linux,darwin}.txt` son los ajustes por plataforma; todos empiezan en cero. El build efectivo es base + ajuste. Build deberá incrementar la base una vez e inyectar `buildNumber`, `BuildDate` y `BuildTime` con `-ldflags` sobre `main.buildNumber`, `main.BuildDate` y `main.BuildTime`. Un `go build` directo informa build 0 y fecha/hora desconocidas. `bloom-uninstall.exe version` y `--version` consultan estos datos sin sistema de help ni acceso a la instalación.

Para compilar y probar localmente desde `installer/uninstall`: `go test ./...`; luego `go build -buildvcs=false -o bloom-uninstall.exe .` y `.\bloom-uninstall.exe --version`. `-buildvcs=false` evita que Go dependa del estado Git del checkout. La integración de Build deberá dirigir la salida al destino Windows acordado.

## Inventario de Setup

`installer/conductor/shared/global_paths.js` fija la raíz Windows en `%LOCALAPPDATA%\BloomNucleus`. `installer/conductor/setup/install/installer.js` crea `bin/`, `config/`, `profiles/`, `logs/`, `hooks/` y despliega componentes dentro de la raíz. `installer/conductor/setup/install/service-installer-{brain,nucleus,ollama,opencode}.js` registra `BloomBrainService`, `BloomNucleusService`, `BloomOllamaService` y `BloomOpencodeService` con NSSM. `service-installer-sensor.js` llama a Sensor, que crea `HKCU\...\Run\BloomSensor` (`installer/sensor/internal/startup/startup_windows.go`). `installer/conductor/setup/utils/repair-tools.js` puede registrar `com.bloom.nucleus.bridge` en HKLM o HKCU. `registry-scripts/hkcu.ps1` puede crear políticas de Chrome por ID de extensión; su `cleanup.ps1` borra claves compartidas y **no** se usa. Setup también puede instalar `bloom-extension.vsix` mediante VS Code; no conserva una constancia fiable del ID instalado.

El workspace se obtiene de `config/nucleus.json`, campo `onboarding.organizations[].workspace_path`. Si existe `active_org_slug`, se elige su organización; si hay una sola organización verificable, se usa esa. Si hay varias sin una activa inequívoca, el usuario elige por número entre las rutas descubiertas, sin escribir una ruta nueva. `installation.origin_path` es el repositorio de origen y **no** el workspace; `testWorkspace` y otras rutas de configuración tampoco autorizan borrar `.bloom`. Si falta o es inválido el dato de onboarding, se detiene antes de desinstalar.

Se exige que la `.bloom` descubierta contenga la identidad Nucleus de esa organización y que `rootPath` y `path` coincidan exactamente con el workspace y su Nucleus. Se rechazan redirecciones de ruta. El programa muestra la ruta obtenida de Nucleus, el inventario y la advertencia de pérdida de identidad local, recibos y Mandates; después exige `SI`. El worker vuelve a verificar tanto la configuración como la identidad antes de quitar `.bloom`. Los archivos del proyecto fuera de `.bloom` permanecen. La operación no es reversible: backup/restore de Nucleus es trabajo separado aún no implementado ni verificado.

El inventario se hace con la cuenta que inicia el programa: usa su `%LOCALAPPDATA%` y su `HKCU`, sin pedir que se ejecute todo como administrador. Lee `config/nucleus.json`, `config/metamorph.json` y `config/profiles.json` para contar rutas internas y externas sin mostrar contenidos sensibles. Son referencias de inventario, nunca autorización para borrar destinos externos. Configuración ausente o inválida se informa y se sigue únicamente con recursos comprobables.

Los procesos se inventarían por PID y ruta del ejecutable. El programa muestra avisos específicos para Control Plane API (`bin/bootstrap/bundle.js`), Brain API, Temporal, Nucleus Worker y Svelte/Vite. Para Svelte, que puede usar un `node.exe` externo, exige que la línea de comando apunte a `webview/app/node_modules/vite` dentro del repositorio indicado por `installation.origin_path` y que exista su `vite.config.ts`; un puerto ocupado o un nombre `node.exe` no bastan. Antes de detener cada PID repite la atribución y después comprueba que no queden procesos asociados. Si Windows no permite consultar CIM, el inventario falla expresamente y la desinstalación no comienza; nunca informa falsamente cero procesos.

Solo controla servicios cuya definición apunte a la raíz esperada y entradas de registro cuyos valores apunten a ella. Incluye `BloomSensor`/`BloomLauncher`, hosts nativos `com.bloom.*`, extensiones Chrome y políticas de extensión identificables por ruta. Las claves padre compartidas de Chrome no se borran. Tras `SI`, prepara un plan acotado a servicios y claves `HKLM` verificadas y solicita UAC con `RunAs`. El proceso elevado vuelve a comprobar pertenencia, retira únicamente esos recursos y no puede borrar la instalación ni el workspace. Si UAC se cancela o falla, no comienza la limpieza de archivos ni de `.bloom`; un fallo tras empezar a retirar servicios puede dejar una limpieza parcial que se informa. La limpieza `HKCU`, procesos y archivos corre desde una copia temporal con el perfil original, aunque UAC haya pedido credenciales de otra cuenta.

Para un test descartable, `BLOOM_UNINSTALL_TEST_ROOT` exige un archivo `.bloom-uninstall-test` en esa raíz; en ese modo no toca servicios ni registro ni solicita UAC. Fuera del test, requiere la raíz canónica de `%LOCALAPPDATA%`. El worker se ejecuta desde una copia en `%TEMP%` para borrar su propio directorio de instalación.

## Límites

No infiere identificadores Backend/D1. Tampoco borra perfiles globales de Chrome, extensiones globales de VS Code ni claves Chrome compartidas sin identificar con certeza el recurso Bloom. Un valor genérico como `ExtensionInstallSources= file:///*` no demuestra propiedad de Bloom y se conserva. No promete limpiar todas las entradas desconocidas de instalaciones históricas. Los servicios admisibles corresponden a los cuatro registrados por Setup; un servicio histórico con otro nombre se reportará como resto no verificado si aparece fuera del inventario actual. Un Setup NSIS mantiene su propio desinstalador. Una instalación con procesos bloqueados o servicios no eliminables deja restos y devuelve error. Las pruebas automatizadas no reproducen un diálogo UAC real ni una elevación con otra cuenta.

La limpieza externa de Backend/D1 requiere cuenta/proyecto/identificador D1 y comprobante de pertenencia a Bloom. No hay hoy una fuente confiable de esos identificadores en Setup, por lo que este binario no ofrece esa operación. Un Setup distribuido mediante NSIS puede haber creado su propia entrada de desinstalación y accesos directos fuera de `BloomNucleus`; son artefactos del empaquetador y deben retirarse con su desinstalador NSIS, no mediante borrado de claves inferidas.
