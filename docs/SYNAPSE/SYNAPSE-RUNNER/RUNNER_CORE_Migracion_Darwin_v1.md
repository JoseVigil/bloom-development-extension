# RUNNER CORE — dossier de migración Windows → Darwin (v1)

**Fecha de inspección:** 2026-10-16. **Estado:** diseño y auditoría estática del checkout actual; **RUNNER CORE no se ejecutó en Darwin**. Este documento no autoriza implementación ni ejecución. Toda ruta Darwin, nombre de artefacto y orden de despliegue propuesto requiere contraste en una máquina Darwin de la arquitectura elegida (`arm64` o `x64`).

## 1. Alcance, fuentes y distinciones

El objetivo es una corrida aislada de **Core posterior a RUNNER**, desde un estado de onboarding ya concluido, que abra Conductor/Core, compruebe Backend y muestre la futura **oferta** de Genesis en Wisdom sin crear ni descargar un Mandate por el mero hecho de abrir Core. La acción explícita posterior del usuario y su contrato de descarga pertenecen al trabajo de Wisdom todavía no implementado. No se deben copiar al Mac el `nucleus.json`, Vault, perfil, ownership, Mandates ni UUID de la corrida Windows.

Fuentes primarias inspeccionadas: `synapse-runner/src/runner-core/` y `synapse-runner/tests/runner-core/`; los tres E2E `tests/e2e/core-genesis-{functional,backend,human-sync}.spec.ts`; `src/surfaces/electron-conductor.ts`; `installer/conductor/workspace/{main_conductor.js,core/preload_core.js,onboarding/ipc/onboarding-handlers.js,package.json}`; `installer/conductor/shared/global_paths.js`; `webview/app/src/{routes/+layout.svelte,routes/wisdom/+page.svelte,lib/bootstrap/genesisLaunch.ts,lib/api.ts}`. El dossier general de RUNNER es `docs/SYNAPSE/SYNAPSE-RUNNER/Synapse_Runner_E2E_Architecture_Dossier.md`; describe onboarding y sus superficies, pero contiene referencias históricas Linux y no constituye prueba de un handoff Darwin. Para el contrato Wisdom, `docs/WISDOM/BLOOM_Wisdom_Handshake_Investigacion_v0_1.md` registra cuestiones aún abiertas; el código actual de `/wisdom` es la fuente sobre el estado implementado.

**Tres gates distintos hoy:**

| Gate | Lo que prueba en Windows | Límite para Darwin / nuevo objetivo |
|---|---|---|

Fuerza un primer POST fallido y observa replay. | Es precisamente el comportamiento que se retirará. No verifica Backend real ni Wisdom. En el historial Windows hubo evidencia de creación durable e idempotencia por gates separados y un intento de Human Sync con respuesta de proveedor que terminó en validación de esquema; ninguna de esas observaciones acredita una corrida Darwin ni la oferta de Wisdom. El antiguo `PROVIDER_TIMEOUT` es otra incidencia, no un resultado de migración.

## 2. Comportamiento actual que impide el nuevo contrato

1. `onboarding-handlers.js` (`onboarding:complete`, alrededor de líneas 1032–1145) ejecuta `nucleus --json authority sync`; para un proyecto **nuevo** con `genesis_launch_required === true` escribe `onboarding.pending_genesis_launch` con `mandateLaunchId`, `projectId`, nombre y ruta. Para proyecto existente/importado borra ese pending. Marca `completed:true` y abre una nueva ventana Core.
2. `main_conductor.js` (`createWorkspaceWindow`, alrededor de 251–274, y boot 625–744) exige `nucleus.json` e instalación completos, ejecuta `nucleus dev-start` antes de la ventana y carga `workspace_url` con `core/preload_core.js`. En modo post onboarding intenta boot completo, con Control Plane; el boot fallido puede mostrar una opción de continuar. Para el gate se exige evidencia de salud real, no sólo una ventana visible.
3. `preload_core.js` expone `readPendingGenesisLaunch`, `ackPendingGenesisLaunch`, `recoverGenesis`, `genesisProjectStatus` y `createMandate`. El read del pending **no lo borra**; el acknowledge adopta la relación mediante Nucleus y después borra el pending (`onboarding-handlers.js`, alrededor de 1154–1210).
4. `webview/app/src/routes/+layout.svelte` llama `runPendingGenesisLaunch().finally(requestMandateReconciliation)` en `onMount` (alrededor de 74–81). `genesisLaunch.ts` (126–187) lee el pending, hace `POST /api/v1/mandates` vía `createMandateApi` y luego acknowledge. La reconciliación GET/WS es distinta del POST creador: hay que observar ambas para separar *lectura* de *creación*.
5. `webview/app/src/routes/wisdom/+page.svelte` es sólo un stub “Próximamente”; no hay oferta operativa de Genesis ni acción explícita de descarga allí. La presencia de un ítem Wisdom en el sidebar no satisface el contrato.

**Consecuencia:** con el código actual y un pending de proyecto nuevo, “abrir Core no crea Mandate” debe **fallar**. No se puede declarar PASS usando un proyecto importado sin pending, suprimiendo el `onMount`, apagando Backend o interceptando el POST: eso evitaría el comportamiento, pero no demostraría el cambio de producto. El test vigente `core-genesis-functional.spec.ts` sirve como caracterización positiva de la automatización antigua y habrá que retirarlo o reconvertirlo cuando Wisdom tome la responsabilidad. No atribuirle cobertura futura.

### 3.1 Gates y archivos de pruebas concretos

- Los tests Windows `windows-functional-root.test.ts`, `windows-functional-launcher.test.ts`, `windows-genesis-backend-{root,launcher}.test.ts`, `windows-gene-g2.integration.test.ts` y `windows-isolation.integration.test.ts` saltan o dependen de Windows. `run-windows-core.test.ts` sólo audita la entrada Windows. No modificar sus expectativas para que “pasen” en Mac; añadir evidencia Darwin homóloga.
- `isolation-preflight.test.ts` **afirma** que `platform:'darwin'` falla con `platform_not_linux`; `linux-proc-inspection.test.ts` sólo ejecuta parte real si `linux`. `isolated-root-assembler.test.ts`, `isolated-launcher.test.ts` y `run-teardown.test.ts` contienen fixtures de `/proc`. Pueden probar funciones puras, pero no habilitan ejecución Darwin.
- `import-boundary.test.ts` limita importaciones del core genérico, incluida carga de `.env`; ampliar su inventario cuando existan adaptadores Darwin para no incorporar accidentalmente secretos o el preflight de onboarding.
- Gate 2 real (`genesis-backend-api.ts`) usa `server.inject` in-process y parchea el singleton de WebSocket durante el test. Un gate Darwin UI→Backend real debe observar HTTP de red y su servidor del run; no llamar `server.inject` “exactamente un POST desde Core”.

## 4. Contrato de entrada posterior a RUNNER

RUNNER es responsable del onboarding Darwin previo. Este dossier **depende de un dossier de RUNNER Darwin aún por aportar/validar** para el modo de construcción del perfil, endpoints, instalación, cierre, logs y estado que entrega. Aquí sólo se especifica qué debe **leer y verificar** RUNNER CORE, sin volver a ejecutar onboarding:

1. `installation.completed === true` y `onboarding.completed === true` dentro del `nucleus.json` **aislado**; `active_org_slug` identifica exactamente una organización y `active_project_id` exactamente un proyecto seleccionado.
2. `backend_identity_org_id === organizations[active_org_slug].organization_id === organizationId` devuelto por Fase 0 **en ese mismo run**; `tenant_id` no vacío y `.ownership.json` correspondiente con la misma identidad/tenant. Verificar `authority_base_url` contra el Backend del run, sin apuntar a D1 ni URL productivos.
3. `workspace_path`, `project_path`, Nucleus base, perfil maestro, userData de Electron, Vault, AITAP, Temporal, logs y caches resuelven dentro de R. Los symlinks, aliases o rutas canónicas que salgan de R detienen el gate. Ningún UUID, token, principal, project path ni snapshot Windows se copia al Mac.
4. Registrar el tipo de proyecto y el pending recibido. Para **proyecto nuevo**, el código actual deja `pending_genesis_launch` y esa es la entrada obligatoria para demostrar que abrir Core **no** lo consume ni hace POST una vez que Wisdom cambie el flujo. Para proyecto existente/importado, documentar ausencia de pending, pero no usar esa rama como sustituto de la prueba negativa.
5. Capturar antes del launch la cantidad de Mandates locales y remotos, el journal/workflow de Temporal, los recibos, el pending, las llamadas HTTP y los hashes de control. No tocar estado productivo. El handoff debe ser un artefacto estructurado del run con rutas canónicas, identificadores y hashes, no una ruta manual en `~/Library`.

## 5. Diseño de una corrida Darwin desde cero (propuesta, no ejecutada)

**Fase 0 — elección de host y artefactos.** Elegir Mac y arquitectura real; verificar Node, Go, Electron bundle y Bloom binaries de esa arquitectura, firma/layout del bundle, rutas de Nucleus y backend. Resolver con lectura de código/runtime si `BLOOM_APPDATA_DIR` y `BLOOM_NUCLEUS_BASE_DIR_OVERRIDE` gobiernan **todos** los procesos; `main_conductor.js` hereda todo `process.env` al lanzar Nucleus, por lo que el allowlist debe eliminar referencias productivas. Si no se puede probar el aislamiento del Vault/Keychain, el gate se bloquea antes de RUNNER/Core.

**Fase A — antes de crear R.** Inventariar archivos y rutas productivas del Mac (sin leer ni imprimir secretos), usuario efectivo, sesiones, procesos Bloom/Backend/Temporal/Chromium y escuchas IPv4/IPv6 relevantes. Elegir un padre controlado fuera del checkout y del HOME productivo; verificar permisos, ruta canónica y que no haya enlace simbólico. Resolver los puertos concretos del run y las variables del child. Fail-closed ante PID/owner desconocido o inspección fallida. No asumir que 48215, 5173 o 7233 están libres: `main_conductor.js` y Core tienen defaults fijos, por lo que si se parametrizan deben ser iguales en Nucleus, Webview y Backend; si no se parametrizan, exigir esos puertos libres y reservarlos para R.

**Fase B — preparar R y RUNNER.** Crear `R` único (`rc-<id>`), manifest de archivos con hashes, `R/home/Library/BloomNucleus`, `R/tmp`, workspace/proyecto sintéticos, userData, logs y bases locales. Copiar solamente binarios/builds de prueba y verificar contenido, arquitectura, firma, permisos y ausencia de secretos/symlinks. Ejecutar RUNNER Darwin desde cero **dentro de R**, con Backend/D1 de prueba y organización/proyecto/identidad sintéticos; no modificar una instalación personal. Tomar el handoff descrito en §4 y cerrar efectivamente todos los procesos de onboarding que no continúen en Core. Si el producto no permite esa separación de procesos sin leer una instalación personal, declarar bloqueo de aislamiento.

**Fase C — entrada a Core.** Antes de abrir, registrar el pending de proyecto nuevo y baseline de Mandates, POST, GET, descargas, receipts y workflows. Iniciar el ejecutable del bundle **copiado bajo R** con entorno mínimo y stdout/stderr abiertos, no desconectados; registrar PID y descendientes. Conductor debe leer el `nucleus.json` de R, `onboarding.completed=true`, ejecutar `nucleus dev-start` en modo Core y cargar `workspace_url` de R en una ventana que exponga `window.onboarding` desde `preload_core.js`. Exigir salud de Nucleus/Control Plane y Backend, respuesta del endpoint de sólo lectura y conexión WS, con atribución del puerto al PID de R. Una ventana visible con warning de boot no basta.

**Fase D — prueba negativa del nuevo comportamiento.** Sin hacer clic en oferta/descarga, abrir Core, navegar entre Home y Wisdom, recargar y reiniciar el bundle. Instrumentar las llamadas del cliente y el servidor antes de la primera navegación: `POST /api/v1/mandates` creador = **0**; descargas de paquete/artefacto = **0**; receipts/ack nuevos = **0**; `pending_genesis_launch` intacto o transformado sólo por un contrato Wisdom explícito aprobado; Mandates locales/remotos, `mandate_state.json` y workflows = **sin incremento**. Las lecturas GET y reconciliación WS pueden ocurrir; documentarlas por separado. Una observación incompleta no es PASS. La oferta debe presentarse desde Wisdom con identidad/versión/procedencia verificables según el futuro contrato; hoy esa aserción está bloqueada por el stub.

**Fase E — flujo Wisdom futuro, en otra prueba.** Una vez aprobado e implementado: acción explícita sobre la oferta, confirmación humana, descarga/instalación o creación según el contrato final, idempotencia y evidencia de ownership/mandate. Definir en Wisdom qué significa “oferta”, qué se descarga, qué endpoint y qué recibo se persiste antes de escribir el E2E. No introducir una descarga sintética ni una mutación automática para hacer pasar el gate negativo. Human Sync, approve, activate, AITAP y Gemini son etapas posteriores y no entran en la corrida inicial.

**Fase F — teardown.** Guardar trace, stdout/stderr, request log, IDs y hashes **dentro de R** y redactar secretos. Cerrar Core, Backend, Nucleus, Temporal, Chromium y nietos sólo si el registro de PID + nacimiento + ejecutable + root los atribuye al run. Confirmar cierre real y liberación de puertos; una señal enviada no alcanza. Comparar estado productivo y remoto con baseline. Conservar R si falla para diagnóstico, o eliminarlo sólo mediante un comando explícito posterior que valide ruta canónica/manifest y que el usuario apruebe; no borrarlo por patrón amplio ni señalar procesos ambiguos.

### 5.1 Comandos orientativos para el futuro run Darwin

## 6. Evidencia, primer fallo y aceptación

La traza por fase debe contener `runId`, arquitectura, raíces canónicas, hash del bundle/ASAR, entorno permitido **sólo nombres de claves y rutas no sensibles**, producto/proceso/PID/tiempo de creación, puertos/owners, salud de Nucleus/Backend, URL real de Core, preload disponible, identidad del proyecto, estado pending, snapshot de Mandates/workflows y contador de POST/descargas. Los registros HTTP deben incluir método, URL local, status, correlación y timestamp; nunca tokens, cuerpo secreto ni credenciales. Guardar primera divergencia con fase, expectativa, observación concreta y log de proceso/HTTP correspondiente. Prioridad diagnóstica: (1) preflight/aislamiento; (2) paquete o launch; (3) Nucleus/Backend; (4) preload/URL; (5) tráfico POST/descarga; (6) UI Wisdom. Detener ahí; no reparar el estado para seguir.

Una corrida Darwin es válida únicamente si: fase A/B/C PASS con evidencia de aislamiento suficiente; el handoff de RUNNER corresponde a **esa** organización/proyecto sintéticos; Conductor/Core abre desde R y Backend responde; no hay POST, descarga, receipt ni workflow creador por abrir/recargar/reiniciar; la UI de Wisdom muestra la oferta según contrato **cuando exista**; los procesos y puertos cierran; el estado productivo permanece invariante. Mientras Wisdom sea stub, sólo podrá emitirse un resultado **PARCIAL/BLOQUEADO POR WISDOM** después de pasar la prueba negativa, nunca PASS de la oferta completa. Con el `runPendingGenesisLaunch()` actual y pending de proyecto nuevo, el resultado esperado es FAIL en el primer POST automático.
