# RUNNER CORE — dossier de migración Windows → Darwin (v1)

**Fecha de inspección inicial:** 2026-10-16. **Actualización de recorrido:** 2026-10-18. **Estado:** diseño y auditoría estática del checkout actual; **RUNNER CORE no se ejecutó en Darwin**. Este documento no autoriza implementación ni ejecución. Toda ruta Darwin, nombre de artefacto y orden de despliegue propuesto requiere contraste en una máquina Darwin de la arquitectura elegida (`arm64` o `x64`).

## 1. Alcance, fuentes y distinciones

El objetivo es una corrida aislada de **Core posterior a RUNNER**, desde un estado de onboarding ya concluido. **Recorrido decidido por José:** Core muestra en Wisdom los Mandates obtenidos del Backend; el Paladín navega y selecciona explícitamente el Mandate inicial; Nucleus lo descarga, verifica e instala; antes de ejecutarlo AITAP permite elegir proveedor por Intent. Abrir Core o terminar onboarding no debe crear, descargar ni instalar un Mandate. **«Genesis» es sólo un label**, nunca la orden implícita de crear un Mandate o iniciar un workflow. La selección, descarga, instalación y elección de proveedor requieren contratos e implementación todavía pendientes. No se deben copiar al Mac el `nucleus.json`, Vault, perfil, ownership, Mandates ni UUID de la corrida Windows.

Fuentes primarias inspeccionadas: `synapse-runner/src/runner-core/` y `synapse-runner/tests/runner-core/`; los tres E2E `tests/e2e/core-genesis-{functional,backend,human-sync}.spec.ts`; `src/surfaces/electron-conductor.ts`; `installer/conductor/workspace/{main_conductor.js,core/preload_core.js,onboarding/ipc/onboarding-handlers.js,package.json}`; `installer/conductor/shared/global_paths.js`; `webview/app/src/{routes/+layout.svelte,routes/wisdom/+page.svelte,lib/bootstrap/genesisLaunch.ts,lib/api.ts}`. El dossier general de RUNNER es `docs/SYNAPSE/SYNAPSE-RUNNER/Synapse_Runner_E2E_Architecture_Dossier.md`; describe onboarding y sus superficies, pero contiene referencias históricas Linux y no constituye prueba de un handoff Darwin. Para el contrato Wisdom, `docs/WISDOM/BLOOM_Wisdom_Handshake_Investigacion_v0_1.md` registra cuestiones aún abiertas; el código actual de `/wisdom` es la fuente sobre el estado implementado.

**Tres gates distintos hoy:**

| Gate | Lo que prueba en Windows | Límite para Darwin / nuevo objetivo |
|---|---|---|
| CORE-00 (`windows-isolation-*`, `native/windows-core-isolation/main_windows.go`) | Prototipo de raíz, ACL, token/desktop y Job con pruebas de acceso, manifest y puertos. `run-windows-core.ts` es su entrada. | El helper es Win32; no se puede afirmar un aislamiento equivalente con `chmod` ni trasladar la evidencia de Job. |
| Funcional (`core-genesis-functional.spec.ts`) | Copia un Workspace empaquetado a una raíz desechable, usa servicio HTTP **simulado**, abre Core y verifica que un `pending_genesis_launch` provoca POST automático, receipt y ausencia de POST adicional tras recarga. Fuerza un primer POST fallido y observa replay. | Es precisamente el comportamiento que se retirará. No verifica Backend real ni Wisdom. El fixture declara `functional_only`; su token normal puede leer rutas productivas. |
| Backend / Human Sync (`core-genesis-backend.spec.ts`, `core-genesis-human-sync.spec.ts`) | El primero usa ruta Fastify real vía `server.inject`, Temporal y watcher desechables; prueba `mandate_state.json`, evento y workflow únicos, replay/restart. En el historial Windows hubo evidencia de creación durable e idempotencia por gates separados y un intento de Human Sync con respuesta de proveedor que terminó en validación de esquema; ninguna de esas observaciones acredita una corrida Darwin ni la oferta de Wisdom. El antiguo `PROVIDER_TIMEOUT` es otra incidencia, no un resultado de migración.

## 2. Comportamiento actual que impide el nuevo contrato

1. `onboarding-handlers.js` (`onboarding:complete`, alrededor de líneas 1032–1145) ejecuta `nucleus --json authority sync`; para un proyecto **nuevo** con `genesis_launch_required === true` escribe `onboarding.pending_genesis_launch` con `mandateLaunchId`, `projectId`, nombre y ruta. Para proyecto existente/importado borra ese pending. Marca `completed:true` y abre una nueva ventana Core.
2. `main_conductor.js` (`createWorkspaceWindow`, alrededor de 251–274, y boot 625–744) exige `nucleus.json` e instalación completos, ejecuta `nucleus dev-start` antes de la ventana y carga `workspace_url` con `core/preload_core.js`. En modo post onboarding intenta boot completo, con Control Plane; el boot fallido puede mostrar una opción de continuar. Para el gate se exige evidencia de salud real, no sólo una ventana visible.
3. `preload_core.js` expone `readPendingGenesisLaunch`, `ackPendingGenesisLaunch`, `recoverGenesis`, `genesisProjectStatus` y `createMandate`. El read del pending **no lo borra**; el acknowledge adopta la relación mediante Nucleus y después borra el pending (`onboarding-handlers.js`, alrededor de 1154–1210).
4. `webview/app/src/routes/+layout.svelte` llama `runPendingGenesisLaunch().finally(requestMandateReconciliation)` en `onMount` (alrededor de 74–81). `genesisLaunch.ts` (126–187) lee el pending, hace `POST /api/v1/mandates` vía `createMandateApi` y luego acknowledge. La reconciliación GET/WS es distinta del POST creador: hay que observar ambas para separar *lectura* de *creación*.
5. `webview/app/src/routes/wisdom/+page.svelte` es sólo un stub “Próximamente”; no hay oferta operativa de Genesis ni acción explícita de descarga allí. La presencia de un ítem Wisdom en el sidebar no satisface el contrato.

6. Hay una **segunda vía automática independiente del `onMount`**. `onboarding:complete` ejecuta `nucleus authority sync`; en `installer/nucleus/internal/governance/authority_command.go` el sync llama `mandatedelivery.Client.Receive` y, si la entrega tiene estado `accepted` o `replay`, materializa automáticamente `mandate.json` mediante `mandateinstall.MaterializeFile`. `backend/src/index.ts` expone `GET /v1/mandate/bootstrap`, que `backend/src/mandate-delivery.ts` resuelve desde `organization_bootstrap_mandates`, lee el objeto R2, comprueba SHA-256 y firma la entrega para la instalación. `nucleus mandate install --id` (`installer/nucleus/internal/orchestration/commands/mandate_install.go`) **ya existe**, pero opera sobre un recibo previamente verificado: no descarga por sí solo ni prueba selección del Paladín. Por eso quitar solamente `runPendingGenesisLaunch()` no garantiza que terminar onboarding deje los Mandates intactos. Esta evidencia del código actual corrige la lectura incompleta de las secciones posteriores de la versión inicial de este dossier.

**Consecuencia:** con el código actual, un proyecto nuevo con pending puede crear por el `onMount`; una asignación bootstrap disponible puede descargarse e instalarse durante `authority sync` al cerrar onboarding, incluso antes de abrir Core. Las dos fuentes de efectos deben neutralizarse conforme al contrato aprobado, sin apagar Backend ni ocultar el pending para hacer pasar el test. El test vigente `core-genesis-functional.spec.ts` caracteriza la automatización antigua; no acredita el recorrido Wisdom.

## 4. Contrato de entrada posterior a RUNNER

RUNNER es responsable del onboarding Darwin previo. Este dossier **depende de un dossier de RUNNER Darwin aún por aportar/validar** para el modo de construcción del perfil, endpoints, instalación, cierre, logs y estado que entrega. Aquí sólo se especifica qué debe **leer y verificar** RUNNER CORE, sin volver a ejecutar onboarding:

1. `installation.completed === true` y `onboarding.completed === true` dentro del `nucleus.json` **aislado**; `active_org_slug` identifica exactamente una organización y `active_project_id` exactamente un proyecto seleccionado.
2. `backend_identity_org_id === organizations[active_org_slug].organization_id === organizationId` devuelto por Fase 0 **en ese mismo run**; `tenant_id` no vacío y `.ownership.json` correspondiente con la misma identidad/tenant. Verificar `authority_base_url` contra el Backend del run, sin apuntar a D1 ni URL productivos.
3. `workspace_path`, `project_path`, Nucleus base, perfil maestro, userData de Electron, Vault, AITAP, Temporal, logs y caches resuelven dentro de R. Los symlinks, aliases o rutas canónicas que salgan de R detienen el gate. Ningún UUID, token, principal, project path ni snapshot Windows se copia al Mac.
4. Registrar el tipo de proyecto y el pending recibido. Para **proyecto nuevo**, el código actual deja `pending_genesis_launch`: es una entrada adversarial útil para demostrar que Core **no** lo consume ni hace POST. El futuro contrato puede retirarlo o transformarlo en contexto no ejecutable, pero eso debe decidirse y auditarse. Para proyecto existente/importado, documentar ausencia de pending, sin usar esa rama como sustituto de la prueba negativa.
5. Capturar **antes de `onboarding:complete`** el inventario de `organization_bootstrap_mandates` del Backend de prueba, artefactos/recibos del run, `mandate.json` locales y tráfico de `/v1/mandate/bootstrap`. La prueba debe incluir una oferta bootstrap real, porque sin ella `authority sync` no ejercita la vía de autoentrega. Comparar inmediatamente después de `onboarding:complete`: `authority sync` puede actualizar Authority/tenant, pero no debe recibir ni instalar Mandates. El handoff debe incluir esa prueba, la cantidad de Mandates locales/remotos, journal/workflow Temporal, pending, llamadas HTTP y hashes de control; no basta una ruta manual en `~/Library`.

## 5. Diseño de una corrida Darwin desde cero (propuesta, no ejecutada)

**Fase 0 — elección de host y artefactos.** Elegir Mac y arquitectura real; verificar Node, Go, Electron bundle y Bloom binaries de esa arquitectura, firma/layout del bundle, rutas de Nucleus y backend.
